# Подключение входа через Google

Подготовлено 24 сентября 2026 года. Google-вход, разрешённые почты, заявки и панель управления реализованы в `server/`. В шаблонах задан владелец `liryzliryz34@gmail.com`; настоящие ключи Google ещё не заданы. На текущем сайте действует закрытый доступ через ChatGPT; `login.html` показывает только оформление будущего Google-входа.

Пошаговый вариант размещения с готовым `render.yaml`: [DEPLOY_RENDER.md](DEPLOY_RENDER.md).

Памятка для повседневной работы: [ADMIN_GUIDE.md](ADMIN_GUIDE.md). После подключения та же помощь доступна владельцу на `/admin/help`.

## Что потребуется для первого запуска

| Параметр | Что указать |
| --- | --- |
| `GOOGLE_CLIENT_ID` | Идентификатор OAuth-клиента типа Web application в твоём проекте Google Cloud. |
| `GOOGLE_CLIENT_SECRET` | Секрет этого OAuth-клиента. Вводится в секретные переменные хостинга или локальный `.env`. |
| `OWNER_GOOGLE_EMAIL` | `liryzliryz34@gmail.com` — уже задана в шаблонах. Для первого входа владельца требуется Gmail или Google Workspace. |
| `APP_URL` | Окончательный HTTPS-адрес сайта без пути. На Render можно оставить незаданным: используется штатный `RENDER_EXTERNAL_URL`. |
| `AUTH_DB_PATH` | SQLite на постоянном диске. По умолчанию `private-data/google-auth.sqlite`. |

Права владельца Discord-сервера, ID сервера, роли и бот больше не нужны. Членство сотрудников в проекте проверяется вручную при выдаче и отзыве допуска.

Не присылайте Client Secret, пароли, содержимое `.env` или базу в переписку. Client ID и почта владельца не являются секретными ключами, но все параметры лучше настраивать в одном месте на хостинге.

## Один раз настроить Google

1. Открыть [Google Cloud Console](https://console.cloud.google.com/) и создать или выбрать собственный проект.
2. В Google Auth Platform настроить Branding: название приложения «Мандариновый Комплекс», контакт поддержки, адрес сайта и ссылку на сведения о данных `https://ВАШ-ДОМЕН/privacy.html`. Контакт поддержки — реальная почта ответственного за сайт.
3. Выбрать подходящую аудиторию приложения. Для команды с обычными личными Gmail нужен внешний доступ, а не ограничение одной организации Workspace. Следовать требованиям Google к тестовым пользователям и публикации, которые показывает консоль для выбранного режима.
4. Создать OAuth Client типа **Web application**. Зарегистрировать точный Authorized redirect URI:

   ```text
   https://ВАШ-ДОМЕН/auth/google/callback
   ```

5. Сохранить Client ID и Client Secret в серверной конфигурации. Для этого входа запрашиваются только `openid email profile`; доступ к Google Drive, Gmail и файлам не требуется.

Для локальной проверки можно зарегистрировать `http://127.0.0.1:8787/auth/google/callback`. OAuth-переход выполняется на страницу Google целиком, без ввода пароля на сайте комплекса.

## Запуск серверной версии

Нужны Node.js 24.19+ в поддерживаемой ветке, npm и постоянный диск. Выполнить из корня распакованного проекта:

```bash
npm ci --omit=dev --ignore-scripts
cp .env.example .env
```

Заполнить `.env`, затем:

```bash
npm start
```

Сервер по умолчанию слушает `127.0.0.1:8787`. Без обязательных настроек он показывает страницу входа с неактивной кнопкой и не выдаёт справочник. После заполнения настроек нужно перезапустить процесс.

На серверном хостинге вместо файла `.env` можно задать переменные через его панель. `npm start` работает и без локального `.env`, если переменные уже заданы средой.

Для контейнерного хостинга может понадобиться `HOST=0.0.0.0`; порт в этом случае должен быть доступен через HTTPS-прокси хостинга. `APP_URL` содержит конечный адрес в браузере, даже если прокси обращается к Node.js по локальному HTTP.

Render сам задаёт `PORT` и `RENDER_EXTERNAL_URL`. Не переносите туда локальный `APP_URL=http://127.0.0.1:8787` из примера. Для своего домена задайте `APP_URL` явно до первого подключения Google. Проверка `/healthz` возвращает только `{"ok":true}`, если процесс и база работают, даже пока OAuth не настроен. Этот ответ не означает, что Google-вход уже подключён; материалы в таком состоянии закрыты.

## Требования к размещению

- Все пути сайта, включая `/data.js`, `/catalog.js`, `/departments.js` и `/app.js`, должны обрабатываться Node.js. Публичная раздача `dist` отдельно от сервера обходит защиту.
- Внешний доступ — только через HTTPS. `.env`, база, исходники, ZIP и резервные копии не должны попадать в публичный каталог.
- Нужен один процесс приложения и постоянный локальный диск для SQLite. Несколько экземпляров с отдельными базами будут расходиться в допусках и сессиях.
- Прокси/CDN не должен кэшировать приватные ответы. Приложение выставляет `Cache-Control: private, no-store`.
- Не записывать query string `/auth/google/callback` в access log прокси: в нём находится одноразовый код входа. Само приложение эти URL не журналирует.
- Ограничивать попытки входа по реальному IP на прокси. Встроенный лимит учитывает адрес соединения и не доверяет произвольному `X-Forwarded-For`; за одним прокси пользователи могут делить общий лимит.
- Старую копию сайта оставлять закрытой. Права в оригинальных Google Документах настраивают их владельцы отдельно.

Настройки `.openai/hosting.json` описывают существующую статическую публикацию в Sites. Она пока использует вход ChatGPT. Поддержка собственного Google OAuth в доступной документации этой площадки не подтверждена, поэтому защищённая Google-версия подготовлена отдельно для Node.js-хостинга. Не открывайте статический сайт для всех в расчёте на файлы `server/`: они в статической публикации не выполняются.

## Первый вход владельца

1. Открыть окончательный адрес защищённого сайта.
2. Нажать «Войти через Google» и выбрать аккаунт, чья почта точно совпадает с `OWNER_GOOGLE_EMAIL`.
3. Владелец получает кнопку **«Доступ команды»** в шапке справочника. Адрес панели — `/admin`.
4. Добавить одну почту сотрудника и проверить его вход. Затем проверить отзыв доступа.

Первый случайный посетитель не может стать владельцем. При первом подтверждённом входе назначенная почта связывается с постоянным Google ID (`sub`). Другой Google-аккаунт с той же почтой автоматически не получает этот допуск.

Вводить нужно адрес, который показывает Google при входе. Система приводит регистр к нижнему, но не переписывает точки, `+`-алиасы и домены адреса самостоятельно.

## Как разрешаются почты

Для Gmail и подтверждённых аккаунтов Google Workspace заранее добавленная почта получает доступ после входа. Если сотрудник уже оставил такую заявку, добавление почты открывает его действующую сессию.

Google-аккаунты могут использовать адреса других почтовых сервисов. Для них старого признака `email_verified` недостаточно, чтобы считать Google владельцем адреса. Такой аккаунт сначала оставляет заявку; владелец справочника сверяет сотрудника и код аккаунта лично, затем нажимает «Одобрить» во вкладке «Заявки». После этого доступ связан с конкретным Google ID.

Список допущенных почт на сайте отдельный от списка доступа в Google Документах. Автоматической синхронизации прав нет.

## Что сохраняется и проверяется

- Официальная `google-auth-library` проверяет подпись Google, издателя, аудиторию и срок токена. Дополнительно проверяются nonce, подтверждённая почта и назначение клиента.
- OAuth использует случайный одноразовый state, привязанный к браузеру, и PKCE S256. Код обменивается только на сервере.
- Токены Google не сохраняются в базе или браузере и не запрашиваются для фонового доступа. Сохраняются профиль, Google ID, почта, допуск, локальные сессии и журнал.
- На каждый запрос материалов проверяются сессия, статус допуска и привязка Google ID к почте. Административные действия доступны только владельцу и требуют CSRF-токен и правильный Origin.
- Cookie в HTTPS имеет `Secure`, `HttpOnly`, `SameSite=Lax` и префикс `__Host-`. В базе хранится хеш случайного идентификатора сессии.
- Сессия действует максимум 7 дней, на аккаунт сохраняется до 5 сессий. Отзыв удаляет все сессии. Повторное одобрение не возвращает удалённые сессии.
- Выход из Google сам по себе не является выходом из сайта. Используйте кнопку «Выйти» на сайте или отзыв допуска в панели. Изменения допуска в Discord автоматически не отслеживаются.
- Журнал хранится 30 дней; старые записи очищаются при следующем запросе. IP-адреса в журнал не записываются.

Система управляет кругом читателей. Разрешённый читатель всё равно может сохранить уже полученные материалы или сделать снимок экрана. Уже начавшийся ответ и скачанную копию отозвать нельзя. Архив исходников также содержит справочник: передавайте его только доверенным людям.

## Резервная копия и смена владельца

Остановить процесс перед файловой резервной копией SQLite или использовать штатное резервное копирование SQLite с учётом WAL. Хранить базу с ограниченным доступом. Не коммитить `.env` и `private-data/` в Git.

База связана с адресом сайта, Client ID и почтой владельца. При их изменении процесс остановится с пояснением, чтобы допуски одного проекта не применились случайно к другому. Для осознанной смены: остановить процесс, сохранить защищённую копию, изменить настройки, задать новый пустой `AUTH_DB_PATH`, затем заново одобрить сотрудников. Ротация одного Client Secret при неизменном Client ID новой базы не требует.

База старой Discord-версии не переносится автоматически. Новый путь по умолчанию — `private-data/google-auth.sqlite`.

## Проверки и предпросмотр

```bash
npm test
npm run preview:login
```

Проверки используют тестовые Google-ответы и локально подписанные токены; настоящая библиотека проверяет подписи, издателя, аудиторию и срок. Сетевых обращений к реальным аккаунтам в тестах нет. Дополнительно проверяются прямые ссылки, заявки, допуски, CSRF, отзыв, перезапуск и HTTP-запуск без настроек.

`dist/login.html` — безопасный статический предпросмотр оформления с неактивным Google-входом. Он не создаёт сессии. В настоящей серверной версии `/login.html` обрабатывается динамически. Браузерная проверка оформления в текущем окружении недоступна; реальный Google OAuth-проход ещё не выполнен.

После подключения проверить обычным браузером вход владельца, допуск сотрудника, отказ постороннему, отзыв доступа и прямую ссылку `/data.js` в приватном окне. Эти проверки требуют настоящего Google-приложения.
